# TOPWHIZ TUR096 — pooled SET ROLE identity and direct SQL cancellation (NO-GO)

Actual pg.Pool(max=1) enforces exclusive JS checkout but **does not** make individual application requests separate database authenticated principals. When SQL session A switches to effective role stage_a and request B subsequently switches same physical backend to stage_b, `session_user` remains pool_login. Third login of pool_login can cancel B's query by PID, bypassing test-only request ownership and lease/epoch fencing. Cross-login independent media/guardian authority cannot cancel pooled backend; pooled role cannot cancel unrelated isolated LOGIN backend. Restricted LOGIN/NOLOGIN and independent guardian schema-owner generation-2 COMMIT are physically verified in disposable PG16 only.

Test-only A/B lease guard is illustrative and never deployed. Granting membership for `SET ROLE` may itself widen privileges; do not equate `SET ROLE`, RESET ROLE, DISCARD ALL, PID identity or application cancellation-token check with SQL IAM. A truly distinct, independent, least-privileged authenticated LOGIN helps block direct unauthorized cross-role `pg_cancel_backend`, but SQL role ownership, connection pool reuse, SQL injection/control of same credentials, owner regrant and cancellation authority must still be considered. Never grant global `pg_signal_backend` or service superuser.
