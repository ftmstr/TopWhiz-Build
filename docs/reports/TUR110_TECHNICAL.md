## Distinct real PostgreSQL16 adversarial acceptance
Disposable PostgreSQL16, one actual node-postgres `pg.Pool(max=1)` physical victim SQL backend reused from request A to B, identical PID and `pg_stat_activity.backend_start`. Six restricted random roles: victim, NOLOGIN `SECURITY DEFINER` function owner, outsider, broker, guardian reader and guardian owner; five independent LOGINs and no `pg_signal_backend` membership. Gate definer inherits only victim backend role, owner schema denies PUBLIC access but explicitly gives limited schema USAGE to outsider and broker so the function privilege itself is the experiment.

**Unsafe phase:** a privileged function that cancels the supplied PID is committed before `REVOKE EXECUTE FROM PUBLIC`; PostgreSQL's default new-function PUBLIC EXECUTE lets an untrusted outsider with schema USAGE invoke it and cancel B's active SQL, even though outsider's direct `pg_cancel_backend` returns SQLSTATE 42501. B SQL is cancelled with 57014. The subsequent REVOKE immediately makes the already authenticated outsider's function call fail 42501.

**Transactional phase:** `CREATE FUNCTION`, owner change, `REVOKE EXECUTE FROM PUBLIC` and limited broker EXECUTE granted inside a single transaction. Before COMMIT, another authenticated login cannot resolve/call the uncommitted function (undefined or denied); after COMMIT outsider has no EXECUTE (42501) and never had an observable PUBLIC EXECUTE window. Even so the explicitly authorized broker, not request-bound to B, can still cancel B's real active SQL (57014), demonstrating that atomic ACL publication alone does not prove caller/request ownership. Revoking broker EXECUTE restores 42501; B's next query completes. Independent guardian-owner COMMIT generation-2 and separate reader readback.
