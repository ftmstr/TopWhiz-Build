# TOPWHIZ TUR126 — Transaction-scoped RESET ROLE is not a durable pool-cleanup fence

PostgreSQL `RESET ROLE` executed inside a transaction can be rolled back. When a pooled SQL backend already has elevated `current_user` from request A, an independent rights administrator's acknowledged membership REVOKE does not necessarily reset that backend's effective role. Request B's `BEGIN; RESET ROLE;` temporarily lowers privilege and denies function EXECUTE (42501), but subsequent transaction ROLLBACK restores previously active executor identity, allowing foreign-query cancellation (57014) through a deliberately vulnerable **test-only SECURITY DEFINER** function. A single SQLSTATE 42501 within an aborted transaction must not be treated as successful permanent privilege release. A standalone RESET ROLE outside the failed transaction denies subsequent EXECUTE (42501) and restores correct third checkout.

Production must independently authenticate caller/request identity, check trust-bound SQL owner and group SET role graph, enforce isolation or complete session reset outside transaction on checkout/release, guard each pool epoch/PID/backend_start, and fail closed under COMMIT uncertainty and physical client disconnect.
