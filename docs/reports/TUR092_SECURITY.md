# TOPWHIZ TUR092 — Security: stale pooled PID may cancel another HTTP request's SQL (NO-GO)

Novel actual PG16 boundary: the exact same server backend PID persists after request A completes and `DISCARD ALL`; another request B checks out this backend. A stale request-A ticket is refused by a test-only epoch/lease/request equality check, but the database does not know that application ticket. A third SQL session logged in as the shared non-superuser media role can still execute `pg_cancel_backend(pid)`, causing B's active query to fail with SQLSTATE `57014`. Independent media-owner and guardian-reader LOGINs are denied cross-role cancellation. No pg_signal_backend membership or superuser to restricted LOGINs. Genuine connection pool handoff tested; OS PID reuse, a real production pool and production enforced cancellation authorization are **NOT PROVEN**.

Root mitigation requirements: do not expose arbitrary backend PID or shared service credentials to other request contexts; associate cancellation with a single retained *exclusive* checked-out connection, close/discard on uncertain ownership, authenticate request-specific lease/epoch in a truly independent authority, and fail-closed on handoff/recycle. An app-only ticket cannot constrain direct same-role SQL. Long-lived shared SQL roles remain a privilege risk. Fully revoking direct pg_cancel_backend without independently enforceable role isolation is unproven.
